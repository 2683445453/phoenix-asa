# 泰克飞船牵引光束目标操作检查（2026-09-23）

## 检查范围

目标是抓住生物后，在牵引光束的“移动目标位置”模式中调整速度和操作距离。与抓取后的回收动作分开判断。使用独立本地测试服 `PhoenixFeatureTest-20260917`（客户端 PID 41500、服务器 PID 49072），只读反射和连续采样定位参数；实验修改仅作用于当前飞船实例，并设定到期恢复。未改正式功能、配置或菜单，未使用 computer use。

## 原生参数与调用路径

实际类为 `/Game/Genesis/Dinos/TEKHoverSkiff/TekHoverSkiff_Character_BP` 的 `TekHoverSkiff_Character_BP_C`。客户端和服务器当前实例默认值相同：

| 字段 | 默认值 | 蓝图使用位置 |
| --- | ---: | --- |
| `BeamMovementSpeed` | 1000 | `Tick_ManipulateBeam`，移动目标位置 |
| `BeamMovementSpeed_RunMult` | 1.5 | `Tick_ManipulateBeam`，冲刺输入分支 |
| `BeamMaxLength` | 5800 | `Tick_ManipulateBeam`、`CalculateBeamViewTracePoints`、`UpdateBeamEndPoint` |
| `beamMinLength` | 100 | `Tick_ManipulateBeam` |
| `MoveBeamChar_MaxRelativeForward` | 800 | `Tick_ManipulateBeam` 的另一个前向限制；本轮没有单独测试其含义与边界 |
| `BeamRetractSpeed` | 800 | `Tick_ManipulateBeam` 的回收分支；不代表目标位置操作速度 |

以上长度、速度为游戏内部单位，通常分别按厘米、厘米/秒理解；精确帧速率还受蓝图的 DeltaSeconds、输入与网络更新影响。

## 双端实测

1. **操作模式基线**：目标相对飞船的距离从约 35 米向远处移动，客户端和服务器均在 58 米停止，与 `BeamMaxLength=5800` 一致。
2. **仅客户端移动速度 1000→2000**：客户端约 35–37 秒段的距离从 46 米降到 17 米，服务器同期从约 51 米降到 38 米；两端都保留各自字段值。客户端变快不等于服务器目标同步变快。
3. **仅客户端最大长度 5800→8700**：客户端在操作模式达到 87 米，服务器仍停在 58 米。因此只改客户端不能使联机目标实际远离到新上限。
4. **独立测试服最大长度 5800→8700**：服务器在操作模式记录到超过 58 米，最高约 72.5 米。说明服务端范围可以扩大；这只验证了有限的 87 米上限，不能称为“无限范围”。该次服务器越过 58 米时，客户端的限时补丁已到期，客户端显示仍被自身 58 米上限钳住，双端表现并不一致。
5. **仅测试服移动速度 1000→2000**：服务器约 2 秒内从 58 米移至 18 米，客户端同期从 58 米移至约 38 米；证明服务器使用该速度字段。单侧修改会产生双端位置差。

`BeamRadius=300` 被 `Find BeamTarget` 引用，影响目标搜索/抓取半径，不应当作抓住后的操作范围。回收速度测试也显示客户端单改 `BeamRetractSpeed=1600` 时服务器仍按 800 回收；该分支不是本次用户所指的目标操作模式。

## 结论与下一步

- **目标移动速度可以改**：蓝图有明确参数入口，客户端与服务器各自使用自己的值。要让联机目标一致移动，至少需要在可控制的服务端同时调整并继续做双端验证。
- **操作距离可以扩大**：本地测试服已实测服务器目标超过默认 58 米。没有验证无限距离；实际应使用有限可配置上限，还要检查遮挡、目标限制、网络位置同步与极大距离的稳定性。
- **当前客户端注入项目尚不能把这两项作为联机有效功能交付**：单改客户端时，服务器保留原速度和 58 米上限。若面向自有服务器实现，需分别加入可恢复的客户端/服务端配置，再完成边界、重连、卸载和双端回归。

实验原始数据：`release/diagnostics/skiff-20260923/` 下的 `client`、`server` 反射快照，`manip-baseline-*.jsonl`、`manip-speed-*.jsonl`、`manip-range-*.jsonl`、`server-speed-*.jsonl`。采样使用 `monitor_skiff_beam.py`；限时修改使用 `experiment_skiff_field.py`。所有临时参数均已在测试结束时恢复，并以双端只读采样复核。

## SDK 来源与服务器蓝图请求路径

项目 `src/external/CppSDK` 是 Dumper-7 从 ASA 客户端运行时反射数据生成的 C++ SDK。`SDK.hpp` 标注生成基础版为 `5.5.4-829680+++ARK1+Rel-1.93`，兼容目标为 `5.5.4-830859+++ARK1+Rel-1.93`；`README.md` 说明源自 v93.9 完整 dump，后来复核核心类布局。泰克飞船属于按需加载蓝图，本轮直接读取运行中客户端和独立测试服的 `TekHoverSkiff_Character_BP_C`，导出反射字段、函数签名、脚本字节码，而不是依赖静态 SDK 中恰好存在该蓝图类。

服务器蓝图的请求签名显示：

- `Server_SyncMovementInputs(MoveInputs: Vector)`：客户端发送移动输入向量；服务器的 `Tick_ManipulateBeam` 引用 `SkiffMovementInputs_LastReplicated`，并读取服务器实例自己的 `BeamMovementSpeed`、`BeamMaxLength`、`MoveBeamChar_MaxRelativeForward`。
- `Server_TryBeamGrab()` 没有目标对象或速度/距离参数；服务器 `TryBeamGrab` 使用 `CurrentBeamHighlightedChar`、燃料、`BeamMaxLength` 等字段。不能把客户端传入任意生物指针视为这条请求的已知能力。
- `Multi_SetBeamCharLocation(Location: Vector, bRelativeSpace: bool)` 是 multicast 接口；`SetBeamCharLocation` 的蓝图参数还包括 `bReplicate` 并调用角色位置设置入口。这不能解释为客户端有一个发送任意目标位置的 Server RPC。
- `CanBeamGrabCharacter` 引用 `CustomTag`、`bIsCarried`、`characterBlackList` 和目标类。当前飞船客户端/服务器实例的 `characterBlackList` 均为空；本轮实测目标为恐爪龙。是否能抓其它生物，还受该函数其余条件及服务器实时状态影响，尚未逐种验证。

因此服务器蓝图可以用于列出候选入口、参数和限制，但仅凭引用表不能证明某个客户端改值会被执行分支采用。当前双端实验已直接证明：单改客户端的移动速度和最大长度不会改变服务器所用的对应参数。
