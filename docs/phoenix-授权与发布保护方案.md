# phoenix 授权与发布保护方案

日期：2026-09-14（初始方案）。2026-09-15 进展：已按本地优先路线接入本机授权服务及客户端验证，参见[本地授权验证说明](phoenix-本地授权验证.md)。下文保留正式部署的目标方案；服务器、正式密钥、加壳与代码签名尚未部署。

最新方向：用户选择以普通用户授权管理为目标，采用本机签发、离线验签、设备与期限校验，有效授权跨软件版本沿用；新版软件由开发者提供。参见[当前离线授权方案](phoenix-离线授权方案.md)，尚未接入。

下文保留最初的 **联网激活 + 服务端到期时间 + 短期签名授权凭证 + DLL 自身验权 + 发布时加壳和签名** 方案作为历史参考，不再是当前优先接入路线。开发继续使用不加壳的本地构建，授权发行版使用独立的构建与打包流程。

加壳能够提高逆向和修改成本，不能保证程序无法反编译、脱壳或破解。仅给 EXE 加壳或加一个激活窗口，也不能阻止别人直接使用 DLL。对于完全在客户电脑上执行的功能，拥有该电脑控制权的人仍可能修改客户端；需要更强控制的核心服务应留在服务器上。

## 1. 初始项目状态（2026-09-14）与计划接入位置

| 项目 | 当前状态 | 后续接入位置 |
| --- | --- | --- |
| C++ 启动器 | 生成 `phoenix.exe`，使用同目录 DLL；尚无授权 | 启动界面输入激活码，显示授权状态、设备和到期时间 |
| C++ DLL | 生成 `phoenix.dll`，负责实际功能；尚无授权 | `src/dllmain.cpp` 的初始化工作线程在初始化功能前验权；运行中持续检查 |

| 开发构建 | 现有 `Release|x64` 保持不加壳，保留本地调试符号 | 新增 `ProtectedRelease|x64`，使用独立的中间目录和发布目录 |
| 分发包 | `dist/phoenix.zip`，当前不含授权保护 | 后续受保护包由专用发布脚本产出，避免误发开发版 |
| DLL 更新 | 旧上游二进制下载入口已关闭 | 新更新服务必须校验签名、产品、版本及文件摘要 |

源码工程文件路径继续沿用原路径；Visual Studio 项目显示名和二进制目标名为 phoenix。原作者及第三方许可证信息保留。

## 2. 建议的授权规则

下面是便于首次实施的默认建议，尚未作为业务规则启用。

| 规则 | 建议 |
| --- | --- |
| 时长 | 日卡／周卡／月卡，可在后台配置 |
| 起算点 | 第一次成功激活时，由服务端一次性写入；重复激活不能重新起算 |
| 设备数 | 默认 1 台，后台支持解绑、换机和人工恢复 |
| 到期时间 | 服务端保存 UTC 时间；界面转成用户本地时间显示 |
| 启动 | 每次启动都联网获取新的短期凭证 |
| 运行中刷新 | 建议约每 3 分钟刷新一次，短期凭证最长 10 分钟；加少量随机间隔分散请求 |
| 断网 | 已验证会话只运行到现有凭证截止时间；截止后暂停受授权功能 |
| 续期 | 后台更新期限，下次刷新取得新期限；已经暂停时提供重新验证入口 |
| 吊销 | 下次成功刷新时停止；断网状态最迟在已有短期凭证到期时停止 |
| 到期处理 | 停止新增功能操作、恢复本软件修改的状态，保留状态提示或安全卸载；不终止宿主程序 |

“每 3 分钟刷新”不意味着允许超期 3 分钟。凭证截止时间必须取 `min(当前服务端时间 + 10 分钟, 许可证到期时间)`，本地运行状态也必须在该期限到达时停止授权功能。若要求后台封禁后几乎立即停止，需要更短的凭证或服务器推送，并接受更高的网络依赖。

## 3. 激活和验权流程

1. 管理后台生成至少 128 位随机熵的激活码，展示给用户；数据库保存验证码的摘要／服务端密钥校验值。激活码不能通过用户姓名、日期等规律推算。
2. 用户在 `phoenix.exe` 输入激活码。客户端通过 HTTPS 提交产品标识、激活码、设备标识、客户端版本和本次随机挑战值。
3. 服务端检查卡密、状态、使用期限、可用设备数、并发会话和最低支持版本。首次激活的计时及设备额度扣减须在数据库事务中完成，避免同时激活多次。
4. 服务端返回短期签名凭证。凭证包括 `product`、`license_id`、`device_id`、`session_id`、`issued_at`、`lease_expires_at`、`license_expires_at`、`server_time`、`nonce` 以及可选的功能集合。
5. 启动器验证签名、产品、设备、挑战值及期限，显示结果。长期会话凭据使用 Windows 用户级安全存储；激活码和完整凭证不写日志、不放 URL 参数、不通过命令行传递。
6. DLL 在自己的初始化工作线程内重新取得或校验绑定当前会话的有效凭证，确认后才注册功能。启动器的“验证通过”布尔值不作为 DLL 的授权依据。DLL 不应依赖启动器一直驻留，现有启动器会在完成加载后退出。
7. DLL 的授权工作线程后台刷新，界面及业务线程读取已验证的授权快照。不要在每帧绘制里联网，也不要在 `DllMain` 的加载锁下联网、弹窗或等待线程。
8. 对失败进行分类：错误卡密、已过期、已吊销立即拒绝；网络超时仅允许使用尚未到期的凭证。重试不能延长旧凭证时间，也不能无限离线运行。

签名建议选择经过验证的标准库与标准格式，例如 ECDSA P-256 的 JWS。客户端固定允许的算法、产品与公钥集合，拒绝 `none`、未知密钥、来自响应的不可信公钥地址、格式异常和重复字段。签名私钥只放服务端的密钥管理设施；EXE、DLL、Lua、仓库和构建包只允许包含验签公钥。

设备绑定减少普通转发使用，需要提供换机处理。普通软件读取的设备标识可以被模拟，不能将它描述成不可伪造的硬件身份；对外只提交最少必要的设备标识，避免上传原始硬件清单。

## 4. 如何避免修改系统时间续命

不能把本机日期或 INI 中的到期日当作可信依据。采用下列组合：

- 由服务端判断是否过期，并在签名凭证里给出服务端时间和有效期限。
- 当前进程用服务端签名时间锚点和单调计时累计经过时间；计时必须覆盖休眠时间，恢复唤醒时也先检查授权。
- 本地期限换算要考虑请求耗时，不能把响应延迟算成额外使用时间。
- 每次重启都要求重新联网；不允许从硬盘恢复旧凭证后重新获得完整的 10 分钟。
- 本次请求随机挑战值必须与签名响应一致，刷新时拒绝过旧响应，防止普通网络回放。

离线签名许可证只能证明内容由签发者签发、未被修改，不能提供可信的现实时间。完全离线、允许客户任意恢复快照且要求可靠防回拨，这三项无法仅靠普通客户端软件同时满足。这是初始方案建议联网授权的原因；当前按用户选择采用离线方案，并接受相应限制。

## 5. 服务端需要建设的最小功能

可以使用现成授权服务，或者自建一个小型 HTTPS 服务和数据库。自建时至少需要：

| 接口／组件 | 作用 |
| --- | --- |
| `POST /v1/activate` | 校验激活码、绑定设备、首次起算、返回会话及签名凭证 |
| `POST /v1/session/refresh` | 校验会话、吊销状态与期限，轮换会话凭据并续发短期凭证 |
| `POST /v1/deactivate` | 受认证的解绑／退出处理；根据规则释放设备额度 |
| 管理后台 | 生成卡密、查询到期、续费、冻结、解绑、查看最少必要的审计记录 |
| 密钥与运维 | 私钥隔离、公钥轮换、数据库备份、时间同步、限流和可用性监控 |

公开客户端接口与管理接口分别授权。刷新凭据被复制后不能无限增加设备或并发会话；设备与会话上限也由服务端事务控制。HTTPS 必须验证证书及主机名，不能复用现有工坊代码中忽略证书主机名错误的网络选项。

## 6. 加壳产品如何选、如何用

可以先试用一种产品，在当前 x64 DLL 与加载流程上完成兼容性验证，再购买对应的商业授权。

| 路线 | 适合情况 | 注意点 |
| --- | --- | --- |
| VMProtect + 独立授权服务 | 需要自定义卡密后台、续费、吊销与联网策略 | 壳与授权服务分开实施；只保护少量关键函数，测试加载、性能与卸载 |
| WinLicense + 授权管理／激活服务 | 希望更多使用现成许可证和机器绑定能力 | 核对所购版本、SDK、自动激活与后台集成能力；仍需设计运行期联网策略 |

VMProtect 的官方文档描述了授权状态、有效期和激活 API；取得序列号后，程序仍需保存并交给授权模块，不能把“已调用激活 API”当成完整授权流程。[VMProtect 授权文档](https://www.vmpsoft.com/vmprotect/docs/licensing-system/)

WinLicense 的官方文档列出设备绑定、按天、固定日期、运行时间等许可证限制，可用于对比许可证形态。[WinLicense 许可证生成](https://www.oreans.com/help/wl/hm_wlom_generating-a-winlicense-licens.htm)

实际接壳步骤：

1. 准备经过授权功能测试的原生 x64 EXE／DLL，保留内部调试符号和未加壳构建。
2. 在所选工具中分别创建 EXE 与 DLL 的保护工程。先对验签、凭证解析、授权状态转换等少量函数应用保护，测量启动耗时与运行开销。
3. 避免一开始对整个游戏 SDK、逐帧绘制、热路径和所有回调做重度虚拟化。复杂 DLL 的 TLS、异常处理、回调与安全卸载需要实际验证。
4. 使用该产品正式 SDK／命令行工具接入发布步骤，保护后的文件写入独立目录，绝不覆盖开发用文件。
5. 对最终加壳后的 EXE／DLL 做 Authenticode 签名，再打包；签名之后不再修改文件内容。

签名用于确认发布者和检测签名后篡改，本身不加密代码，也不代替激活验证。微软 SignTool 支持签名、时间戳和验证；发布流水线使用 SHA-256、时间戳，并验证两个最终二进制。[Microsoft SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool)

## 7. 开发环境与授权发行版分开

建议后续新增构建配置，不依赖用户电脑上的“开发模式”开关：

| 构建 | 授权 | 壳 | 调试符号与输出 |
| --- | --- | --- | --- |
| 当前本地 `Release|x64` | 本次维持现状 | 无 | 保留 PDB，继续本地开发验证 |
| 授权联调构建 | 测试服务及测试公钥 | 无 | 方便调试激活、时间和异常处理 |
| 新增 `ProtectedRelease|x64` | 正式服务，默认拒绝无效授权 | 有 | PDB 仅内部保存，独立发布目录 |

开发绕过只允许由独立构建选择，不能由注册表、配置文件、命令行、环境变量或可复制的“开发许可证”在正式二进制中开启。正式构建的 EXE 和 DLL 都不编入绕过路径；中间文件也分目录，防止增量编译混入开发目标文件。

后续发布顺序：编译 → 授权行为测试 → 加壳 → 签名及签名验证 → 加载／运行／到期／卸载验证 → 生成摘要和发行包。缺少正式服务、公钥、保护工具、签名证书或必要验证时，受保护发布任务失败，不自动降级生成一个看似受保护的普通包。

`build-release.ps1` 默认生成普通开发版 `phoenix.zip`，不应被当作已经接入卡密的版本。2026-09-15 新增的 `build-local-license.ps1` 生成独立的本地授权验证包；这两种构建都没有加壳或签名。

## 8. 正式接入后必须验证的行为

| 场景 | 应有结果 |
| --- | --- |
| 无卡密、错误卡密、畸形凭证、错误签名 | EXE 给出错误；DLL 不启用功能 |
| 绕过启动器直接加载 DLL | 无独立有效授权时仍不启用功能 |
| 复制凭证到另一台设备／另一个会话 | 拒绝或要求重新认证，不增加设备额度 |
| 首次激活并发、重复提交 | 只起算一次，设备数不超限 |
| 运行中到期／服务器吊销／续期 | 到期停止；吊销遵守凭证窗口；续期后按新期限运行 |
| 系统时间回拨、时区改变、重启、休眠、恢复旧凭证 | 不延长服务端有效期限；新进程必须重新联网 |
| DNS、证书、网络或服务器故障 | 无凭证拒绝；已有有效凭证只运行到原截止时间 |
| 缺少正式配置、混入开发目标文件 | 发布构建或验收失败 |
| 加壳与签名后加载、帧率、到期退出、再次加载 | 无明显回归，能够安全停止与卸载 |

## 9. 下一步需要确定的信息

实施前选定：现成授权服务或自建服务；是否采用上述首次激活起算、单设备和断网窗口；所选保护产品及其 SDK；正式服务域名与部署位置；签名证书使用方式。敏感密钥通过密钥管理或本地受限配置接入，不需要发在聊天中。

确认后可按三阶段推进：先完成未加壳的授权联调与测试，再接入正式密钥和服务，最后加入加壳、签名及独立的正式发布流程。
