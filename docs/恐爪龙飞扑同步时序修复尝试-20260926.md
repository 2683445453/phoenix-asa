# 飞扑同步时序修复尝试（2026-09-26）

最新补充：[零起点与 35 米距离扩展](恐爪龙零起点与距离扩展实验-20260926.md)。开启新增选项时发送零起点；下文的真实起点方案仍可通过关闭该选项进行对照。

后续修正：16:29 两轮均因旧跳跃缓存非零在客户端误拦截，未触及本方案的请求发送。已修正该判断，最新版请按 [旧缓存误拦截修复步骤](恐爪龙点扑跃旧缓存误拦截修复-20260926.md) 测试。

本版尝试减少请求期间的客户端提前预测与重复提交，实际是否降低起点偏差、提高连续飞扑成功率待本地服复测。未修改服务器 120 cm 起点容差，未把目标位置冒充服务器当前位置。

## 本轮查到的边界

- 当前骑乘客户端的 `ReplicatedMovement.Location` 是旧位置，与同一时刻本地位置相差超过 1 km；服务器同名字段则是当前值。该字段不能作为客户端的可靠即时校正坐标。
- `SendClientMovementAdjustments` 实际是返回布尔值的条件查询：状态 1–5 返回 false。调用它不会主动同步角色。
- `ClientStartUberpounce` 原包装入口在发出两个服务器 RPC 后立即执行本地 `QueuedUberpounce`，然后启动效果和超时计时器。服务器同时有自己的准备/动画链。
- 已解析 `BlueprintAnimNotifyCustomEvent` 中本实验使用的 Type=1 分支：服务器动画事件可触发 `StartUberPounce(UberpounceQueuedData)`，没有要求必须先由客户端包装入口进入状态 4。该函数其他无关分支存在未支持的指令，未据此宣称所有分支均完成解析。

## 实际修改

1. 点扑跃改为按原顺序调用已核验的 `ServerSetUberpounceStartLoc` 和 `ServerRequestUberpounce`。发送前重新读取真实当前位置；不执行包装入口附带的本地提前准备、效果和本地超时 RPC。
2. 飞扑由服务器原生动画链启动，本地不再在请求刚发出时自行进入准备状态。该变化是同步时序实验，不能视为已证明原包装入口就是全部坐标偏差的来源。
3. 一个请求等待反馈期间不重复提交。观察到本地飞扑状态启动或 `MultiEndUberpounce` 结束反馈后立即结束等待。2 秒没有反馈也结束等待，提示超时，不自动补发。
4. F6 仍没有固定按键冷却；每次必须松开再按。等待反馈与运动状态不满足时明确提示，按键不会排队。
5. 关闭功能、菜单暂停或失去当前坐骑时清除等待状态。默认关闭的点扑跃开关、停止自动化清单和其他运动模式互斥保持。
6. 日志增加 `point_dispatch`（实际发送起点与 `server_animation` 路径标记）、`point_reply`（1=结束反馈，2=启动状态，3=等待超时）以及 `awaiting_reply` 阻止原因。结束反馈本身不证明服务器成功或拒绝，仍按目标/位置/状态对照判断。

## 用户测试步骤

1. 完全退出客户端，再运行包内 `phoenix.exe` 加载新版；回到原本地测试服，骑上恐爪龙。
2. 保持上一组参数：大跳 **3.8 倍**、空中点扑跃 **30 米**。关闭其他运动实验。
3. 在开阔处起跳，朝空处轻按 F6 一次。观察是否仍能正常前扑。
4. 前扑结束后再轻按 F6，尝试连续 5 次。第一组不要快速连按，以便确认服务器动画链仍能正常启动。若完全没有前扑，保存状态提示，无需继续重复。
5. 打开菜单结束保存；关闭点扑跃约 1 秒再开启，可按之前的连按方式录第二组。
6. 告诉我每组前扑次数、是否仍变成慢降，以及是否提示“等待反馈超时”。服务器只读采样用于比对实际接受率和起点偏差。

如果起点误差仍持续存在，本版不会伪造起点或使用过期复制坐标强行移动。后续继续定位原生运动消息与扑跃插值结束时序。

实现：`DeinoPointPounce.inl`、`DeinoActionRules.h::PointReply`、`DeinoActionTrace.inl::EndSequence`。回归覆盖反馈释放、超时无自动重试、暂停清理及原有无冷却按键语义。

只读调查产物：`release/diagnostics/deino-sync-client/`、`deino-sync-server/`、`deino-point-correction/`、`deino-point-prediction/`。
