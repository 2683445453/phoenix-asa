# 穴角兔跳跃速度与空中连跳检查（2026-09-22）

## 检查范围

只读检查现有客户端与独立专服；本轮没有修改穴角兔参数、添加功能开关或绕过服务器检查。客户端 PID 13788，专服 PID 18884，测试根 PhoenixFeatureTest-20260917，端口 7797。原始记录位于 release/diagnostics/rabbit-jump-20260922。

实际类 Jackalope_Character_BP_C，路径 /Game/ASA/Dinos/Jackalope/Jackalope_Character_BP。双端已确认骑乘对象。

## 参数与服务器路径

| 参数 | 双端基线 | 作用证据 |
| --- | --- | --- |
| CustomJumpMaxVelocity | 4500 | CalcCustomJumpVelocity 引用 |
| CustomJumpMinZVelocity | 1500 | CalcCustomJumpVelocity 引用 |
| MaxNumJumps | 3 | CanJumpInternal 将 MultiJumpCounter 与其作 Less_IntInt 比较 |
| MultiJumpCounter | 初始0 | OnJackalopeJump 增加计数，落地后归零 |
| JumpInterval | 1.0 | CanJumpInternal 的时间条件引用；专服分支含系数，不能把字段值当所有状态下的精确间隔 |
| 引擎 JumpMaxCount | 1 | 与实际三次总跳跃不一致，不能单凭这个通用字段判断专用连跳逻辑 |

Server_AttemptCustomJump 的参数仅 Alpha（double，偏移0）和 Direction（Vector，偏移8），不包含最终 Velocity。服务端字节码包装进入 ExecuteUbergraph_Jackalope_Character_BP 的 0x138 入口，再调用 AttemptCustomJump。

AttemptCustomJump（服务器版233字节）的路径：初始化 LocalVelocity → CanJump → 条件分支（不满足跳过）→ FClamp01(Alpha) → CalcCustomJumpVelocity → 保存计算结果 → OnJackalopeJump → Multi_OnJackalopeJump。CanJumpInternal 包含动画状态、步行/下落状态、时间间隔、MultiJumpCounter < MaxNumJumps 等判断。客户端与服务器均有各自这套参数，不能将客户端预测速度当作服务器采用的速度。

与恐爪龙区别：恐爪龙已验证的 ServerRequestJump 接收最终速度向量；穴角兔原生入口由服务器重新计算，不能直接复用此前速度/角度补丁来证明联机有效。超出1的蓄力值也会经过服务器 FClamp01，不是提高最大速度的已验证入口。

证据：client-live、server-live 的 class.json、函数.bin、instances.json；jump-refs.txt、server-jump-refs.txt。rabbit-call-refs.txt 是按字节扫描的引用辅助信息，并非完整反编译，其中少数非对齐扫描出现的乱码不得当作调用；上述关键入口已结合服务器函数完整字节串核对。

## 双端基线

22:39:15 轻点跳跃，服务器水平速度约15m/s；22:39:34、22:39:43、22:40:09 蓄力起跳约43–45m/s。蓄力时长及地形并非严格相同，不能用这些值计算修改倍率；所有参数均保持原值。

最初记录有落地/入水（MOVE_Swimming=4）打断，只到计数2，未据此判定总上限为2。后续22:42:02、:03、:04 和22:42:28、:29、:30，两端均完整记录0→1→2→3，分别在22:42:08及:33落地清零，证实地面一次＋空中两次。第一轮达到3后还记录到客户端跳跃按键时间变化，但未出现第4次服务器计数增长或新的向上速度重置；仅凭该现象不能排除其他并行条件，次数上限判断还由上述蓝图分支支持。

采样设为20ms，值不变不重复写入，实际游戏更新与记录间隔不是固定20ms。用户反馈空中可跳两次，与后续完整记录一致。最终计数事件见 baseline-events-final.json。

## 可修改性结论

- 跳跃速度有明确专用参数入口；尚未做修改后的双端实验，因此本轮不宣称客户端加速可用。要改变服务器计算的速度，优先考虑在自有服务器通过模组/插件调整对应参数，再验证客户端与服务器一致性。
- 空中无限连跳没有已验证的客户端方案。默认总上限3由服务器跳跃检查使用；单改客户端计数或通用 JumpMaxCount 不能视为成功，也没有在本轮擅自尝试清空服务器计数。
- 若后续开发服务端版本，应先用有限上限（例如总5次）证明计数限制能调整，再讨论持续连跳；耐力、间隔和动作条件仍需分别确认。有限测试不等于“无限”已验证。
- 当前结论不等于证明所有客户端路径都不可行，只说明现有成功的恐爪龙方案不适用于此入口，且没有实测成功的穴角兔修改功能。
