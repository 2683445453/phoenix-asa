# phoenix 离线授权方案

状态：方案，尚未接入。当前 `phoenix-local-license` 仍需要本地授权服务；普通 `phoenix` 开发版不要求授权。以下设计不会改变已有激活码和授权数据。

## 当前方向：设备绑定、期限校验、授权跨版本沿用

按用户最新说明，激活码主要用于限制普通用户，不要求抵御所有专业破解。游戏更新后不强制使激活码失效：仍在有效期内、仍使用同一设备的用户，拿到你提供的新版软件后继续使用原授权。新版交付由你管理，不为每次频繁更新增加重新签发的工作。

可以让用户在激活后完全不连接授权服务，连 `127.0.0.1` 的本地服务也不需要。采用你本机签发的授权文件，用户端只保留验签公钥。数字签名用于确认授权内容由你签发且没有被修改；它本身不隐藏内容，也不能让程序无法被修改。[Microsoft CNG 签名与验签](https://learn.microsoft.com/en-us/windows/win32/seccng/signing-data-with-cng)

使用流程：

1. 用户从你这里取得软件，程序导出包含设备标识和产品标识的申请文件。
2. 用户把申请文件交给你。你在自己的电脑上核对购买记录，使用私钥签发 `phoenix.license`。传递文件可以通过 U 盘或其他渠道，软件本身不需要联网。
3. 用户导入文件，启动器和 DLL 分别在本机验证签名、设备和到期时间，全程无需授权服务。
4. 游戏更新后，由你提供适配的新版本。新版本继续接受同一产品、同一设备上仍有效的原授权；升级不会重置或延长使用期限。到期续费或换机时才重新签发。

用户端需要验证授权文件，但不访问授权服务器。私钥和签发工具只在你这里保存，绝不能随软件发给用户。现有随机短激活码依赖数据库查询，不能直接搬到离线模式；可以用申请文件和授权文件，也可以把完整签名许可证编码成较长的激活字符串。

## 授权与更新的具体规则

| 项目 | 约定 |
| --- | --- |
| 激活 | 一台设备导出申请，由你本机签发，用户导入后离线使用 |
| 使用期限 | 签发时确定固定截止日期；启动时和运行期间检查 |
| 版本升级 | 同一产品的有效授权继续使用，不因游戏或软件更新自动作废 |
| 续期 | 你重新签发延长截止日期的授权，升级或重复导入不能续期 |
| 换机 | 你核对记录后重新签发；纯离线无法即时撤回旧设备上的文件 |
| 新版交付 | 由你提供新版软件，不建设公开自动下载入口 |
| 开发环境 | 不加壳、不要求激活 |

保留最初要求的按天使用期限，但采用适合普通用户管理的本地检查。不要把本机首次导入时间当作不可重置的购买起点；截止日期在签发时确定。普通回拨可以检测，拥有管理员权限的用户仍可能修改程序、删除状态或恢复整机快照，纯离线方案不承诺彻底防破解。

本地可保存最近见过的最大时间，检测普通回拨；运行期间用单调计时补充检查。`GetTickCount64` 表示系统启动后的经过时间，无法单独提供跨重启的可信日期。[Microsoft GetTickCount64 文档](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-gettickcount64)

授权缓存可以用当前用户范围的 DPAPI 保护，避免直接拷贝缓存；它不能替代签名或可信时间，也不能防止恢复整个系统快照。[Microsoft DPAPI 文档](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)

## 游戏兼容性与授权分别处理

游戏频繁更新可能缩短旧版软件的可用时间，你持续提供适配版本即可。它不是严格的到期机制：并非每次更新都破坏兼容性，旧程序配旧游戏也可能继续运行。因此不承诺“即使被破解也一定只能使用若干天”，也不为这一预期增加每次更新强制换码的规则。

- 授权文件签名覆盖 `product=phoenix`、许可证格式版本、许可证编号、设备标识、签发日期、截止日期及功能权限，不绑定每次发行的 `release_id` 或游戏版本。
- 软件升级保持许可证格式及公钥兼容；许可证格式版本只有在格式实际变化时才调整。若以后轮换签名密钥，应保留对仍有效旧授权的验签支持，避免正常更新意外要求全部换码。
- EXE 与 DLL 的发行版本匹配属于程序包完整性检查，不影响有效许可证跨版本使用。游戏接口匹配属于兼容性检查，也不改变授权截止时间。
- 升级保留用户导入的许可证；覆盖程序文件、换目录、重新导入都不能重新开始计时。授权文件不打进通用发行压缩包。

数字签名、设备绑定和本地期限校验作为普通用户的授权门槛。加壳、完整性校验和代码签名仍是后续发行保护步骤，仅作用于发行版。

## 在现有项目中接入的位置

实现时新增独立的 Offline 构建模式，保持 Development 不加密、不验权，Local 继续用于已有服务流程测试。离线模式复用现有 CNG 公钥验签基础，但采用独立的离线许可证格式和用途标识，不能把现有短期会话凭证直接当成永久离线授权。

新增本机签发与许可证管理工具、用户申请导出和导入界面；离线构建不编译 HTTP 刷新代码，不带 `license-server.json`。EXE 与 DLL 都要独立检查授权；运行期间到期时沿用现有功能停止和安全卸载流程。生产签发使用专用私钥，已有本地测试私钥不直接用于正式发行。

以后如需自动签发，可将申请校验和签发步骤搬到服务器；运行端仍可保留离线验签。当前不需要部署服务器。签发日期、设备换绑、补发和续期记录在你的本机管理端保存。纯离线换机后旧机器上的有效授权只能等到原期限结束，不能依靠普通软件更新将其即时撤销。

接入验收覆盖：完全停止授权服务且断网仍能使用、缺失或篡改许可证拒绝、其他设备拒绝、有效授权在同一产品的新旧发行版均可使用、升级与重复导入不改变截止时间、到期停止、普通回拨检测、缓存被删除的处理、EXE/DLL 分别校验，以及通用发行包不含私钥或用户授权。当前这些属于待实现验收项。
