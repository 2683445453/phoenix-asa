# 笔记请求提速与命运之潮审查（2026-09-28）

后续实验入口：按用户要求，新增「自动化 → 笔记与上传 → 笔记重复解锁实验」窗口。实验路径不按已解锁状态过滤，允许同一条笔记在上一轮观察结束后再次请求；命运之潮按运行时类型与 Genesis1 标志识别，不硬编码 1345–1354。单条与整组均记录实际请求编号和前后本地读数，观察时长 5 秒，日志位于 DLL 同目录的 `logs`。这为验证下述未归因现象提供入口，不改变原生服务器处理，不把实验请求或本地经验变化当成已确认重复奖励。

本次把软件的笔记队列从每 250 ms 请求 1 条改成每 100 ms 最多请求 4 条，理论发送上限由约 4 条/秒提高到 40 条/秒。它提高的是请求发送速度；服务器仍决定笔记是否解锁、是否给予经验与 Buff。队列保留一次一轮、去重、取消、人物/地图变化停止及点击防重入，卡顿后不会补发积压的大量批次。

用户明确观察到：**再次完整运行软件的「解锁笔记经验 Buff」后，可以重新得到 Buff。** 本次保留这一现象，但尚不能确认第二轮来自哪个笔记 ID，也不能把整轮重跑直接解释为同一条笔记重复奖励。

重复奖励的审查结论：**在本次检查的原生解锁路径中，没有找到同一角色当前存档已记录的笔记可以反复领取笔记经验 Buff 的例外；命运之潮也经过相同的已解锁检查。** 命运之潮的 9 条正文/合集允许不靠近笔记箱子，且没有禁止 XP Buff，但这两个标志都不代表可重复领取。实际远程服务器版本、插件或其他奖励入口仍可能不同，本次没有执行重复解锁实验，未完成对用户现象的归因。

## 原生处理为何拒绝已记录笔记

软件调用的是：

```cpp
ServerUnlockPerMapExplorerNote(ExplorerNoteIndex, false, true);
// false: bAvoidBuff；true: SavePlayerData
```

93.15 服务器原生函数入口 RVA 为 `0x4efd940`。关键顺序如下：

1. 检查索引、DLC 所有权、角色和 PlayerData。命运之潮的所有权调用在 RVA `0x4efdd21`。
2. 查询服务器 PlayerData 已解锁记录。命名笔记检查名称数组，普通索引检查位数组；普通检查调用在 `0x4efde3e`，随后 `0x4efde43 test al, al`、`0x4efde45 jne 0x4efef82`。已记录则直接到退出段。
3. 通过后才检查箱子距离/免距离，并写入笔记记录；索引位写入在 `0x4efe12b`，命名记录写入在更早的 `0x4efe091`。
4. 后段才判断保存参数，再判断 `bAvoidBuff` 与 `bPreventXPBuff`。
5. 最后才调用 `AddExperience` 与 `APrimalBuff.StaticAddBuff`；Buff 调用在 `0x4efee12`。

当前 93.37 客户端中的相同原生路径也做了交叉检查，避免只依赖旧服务器：

- 反射找到 `ServerUnlockPerMapExplorerNote` 的 exec 包装 RVA `0x6006900`；在 `0x6006b01` 调用虚表 `+0x1c00`。
- 对应类默认对象的该虚表槽指向实现 RVA `0x66eaa30`。
- 命名记录检查 RVA `0x66eac4a`，索引位检查 RVA `0x66eac83`，汇合至 `0x66eac88 test al, al`；`0x66eac8a` 在已解锁时跳到退出段 `0x66ebbfb`。
- 后段才检查 `bPreventXPBuff`（`0x66eb9e1`）并添加 Buff（`0x66ebadc`）。

所以，两个被检查版本的该路径均不存在「命运之潮绕过已解锁检查、再次给 Buff」分支。不能从这一结论推定所有第三方服务器、所有蓝图或插件都采用相同奖励逻辑。

### 保存参数不决定本轮是否记录解锁

`SavePlayerData=false` 不会让该笔记在当前会话中保持未解锁。服务器先在 `0x4efe091` 或 `0x4efe12b` 写入内存解锁记录，远在 `0x4efec27` 检查保存参数之前。改变该参数不能用来获得原生的重复 Buff。

### UI 强制显示也不等于再次奖励

`UnlockExplorerNote` / `ClientUnlockExplorerNote` 最终使用 `UnlockExplorerNote_V2`。93.15 的 V2 实现在 RVA `0x4f1f1e1` 仍先调用同一个 `ServerUnlockPerMapExplorerNote`。

V2 的 `actuallyForceShowExplorerNoteEvenWhenAlreadyUnlockedLocally` 影响本地笔记显示判断；它没有移除服务器的已解锁门槛。当前 SDK 与已查原生符号中未找到另一项名为 `ServerUnlockExplorerNote` 的独立奖励 RPC。

## 如何理解「看起来重复给经验」

以下是需要区分的状态，不是对用户观察的实测归因：

- **全局图鉴收藏与当前角色/地图记录不同。** `LocalIsGlobalExplorerNoteUnlocked` 读本地全局收藏；软件筛选用 `LocalIsPerMapExplorerNoteUnlocked`，读取当前 PlayerState 的索引/名称解锁记录。收藏里已经看过的笔记，不必然在另一角色或存档的当前记录中已经解锁。
- **整轮重跑可能使上一轮未成功的其他 ID 成功。** 软件当前只知道请求发出，并未逐条确认奖励来源。因此需要比较两轮各自的实际请求 ID 与服务器结果，才能归因用户报告的第二次 Buff。
- **本地同步状态不等于服务器处理结果。** 本地查询读取 PlayerState 镜像的 `+0x758` 索引位数组或 `+0x768` 名称数组；服务器读取自己的持久角色记录。同步延迟可能让软件重发相同 ID，但若服务器已经记录，所审查的原生路径仍会拒绝，这一点本身不能解释新的 Buff。最后一次只读采样未识别出可确证的当前 LocalPlayer 控制器，因而没有报告当前人物的命运之潮已解锁数量；空匹配记录保存在 `current-local-note-state.json`，不可解读为全部未解锁。
- **不同笔记授予相同名称的 Buff。** 连续请求不同索引可以表现为同一 Buff 再次出现或计时变化；需要按相同索引核对，才能判断是否是同一条笔记重复奖励。
- **可重复里程碑是另一套 XP 奖励。** SDK 有 `RepeatableMilestoneFlatXPTable`、`RepeatableXPThresholds` 和 `ComputeRepeatableMilestoneXP`；存在可重复里程碑 XP 不能推出存在可重复笔记 Buff。
- **剧情回放、补发收藏、插件或旧版行为可能不同。** 需要知道实际入口和服务器版本，才能确认这些情形。

Genesis 故障记录/神秘笔记通过本软件这一 RPC 请求时也受统一已解锁门槛约束。本次 SDK/原生符号检索没有找到能证明其重复给予笔记 Buff 的独立原生入口；当前采样不是 Genesis 地图所有蓝图的完整审计，因此不把「未找到」写成「任何地图玩法都绝不可能」。

## 软件变化及验证边界

请求节奏在 `src/internal/Hack/WorldUtilityRules.h` 的 `NoteRequestBatch` 中；游戏线程派发位于 `src/internal/Hack/WorldUtilities.inl`。仍筛除 `bPreventXPBuff=true` 和当前角色/地图已解锁的条目。取消、完成或会话变化会释放请求状态；运行中再次点击不会从头重启当前队列。

本次已完成对应批次调度、防重入、取消与卡顿不追赶测试，并完成构建。没有把「RPC 已发送」显示成「服务器已成功授予」，也没有实际发送笔记请求来测量游戏内成功率或完成时间。

若要核实某条笔记的重复 Buff，应在允许测试的单机或自有测试服，固定角色、地图、版本和同一笔记 ID：先记录服务器解锁位、Buff 实例/剩余时间与 XP；在已确认首次解锁且同步完成后再测试同一 ID，观察第二次是否新增 Buff 或改变有效持续时间，并保留请求前后的记录。命运之潮应分别核对 1345–1353，另以禁止 XP Buff 的 1354 和普通笔记作为对照。当前结果支持保留已解锁过滤；没有证据支持为所有已解锁条目开启无限重复请求。
