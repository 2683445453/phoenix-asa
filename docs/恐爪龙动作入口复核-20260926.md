# 恐爪龙动作入口复核（2026-09-26）

## 结论

本轮找到可进一步实验的区别：ServerRequestLatchedJump与ServerRequestLatchedAutoJump不是相同的服务端处理。普通抓附跳跃在当前构建中拒绝长度大于2的输入；自动抓附跳跃的已解析事件处理没有这项检查，也没有普通ServerRequestJump的Walking检查。后者进入缓存速度→播放蒙太奇→动画通知→运动更新链。尚未实际调用候选请求，不能宣称已实现空中加速或无目标定空。

重要修正：看到小向量限制时曾推测参数可能是方向向量；继续解析LatchedJump调用方与Latched Jump Launched后，证据支持它仍为最终速度向量。不能通过简单把速度归一化来修复，因为后段没有把它重新乘回目标速度。

## 证据与方法

当前本地服PID31260，沿用已验证SHA256=a2aee3fd6c233b26cdbd2f640c35c36962dad9acee5ef8bd83dc5df38a1422e7的程序和符号缓存。只读读取当前对象注册表、反射函数和字节码；主事件图当前内存与前轮捕获逐字节一致。新增8个原生候选入口的前最多64字节均与磁盘一致。未修改服务器或发送动作请求。

新增decode_deino_actions.py为有限字节码读取器：解析所需表达式、显式跳转、条件跳转和执行流栈操作；不支持的操作立即标STOP，不跳过后猜测。输出保留PUSH_FLOW/POP_FLOW语义及分支边。它不是完整UE反编译器，不把简单图遍历当作动态执行跟踪。普通地面跳跃、两种抓附跳跃的显式可达块解析无STOP且无未展开队列；已用原先人工确认的Walking检查校对。RidingTick和动画处理其他分支仍有未支持操作，具体范围保留在helper-blocks.json。

## 普通抓附跳跃：拒绝大向量

ServerRequestLatchedJump入口0x207a：

- 0x207a对请求Velocity求VSize。
- 0x209f调用Greater_DoubleDouble，常量为2.0。
- 0x20c5条件不成立时跳到0x1892；成立则0x20d3 POP_FLOW退出。
- 可继续的分支检查bHasRider、网络模式、扣耐力，清空LatchedJumpVelocity，保存CachedLatchJumpVelocity，播放对应动画并记录时间。

客户端LatchedJump的手动分支0xa65等处用LatchedJumpSpeed计算最终向量，0xb5d将其传给ServerRequestLatchedJump。因此“本地函数被调用”与“服务器接受最终速度”确实不同。当前服务端LatchedJumpSpeed为5000，单位与移动速度向量一致；阈值2不是2m/s或2倍。此静态检查可解释一个确定的拒绝条件，但没有动态证明此前用户某次操作经过哪条分支，也不能确定这项限制的设计意图。

## 自动抓附跳跃：候选服务器速度链

ServerRequestLatchedAutoJump入口0x20e9跳到0x194c，网络模式分支到0x1855记录LastTimeQueuedAutoJump，再经0xdbc扣耐力。0xa05开始保存请求到CachedLatchJumpVelocity，选蒙太奇、PlayAnimEx、记录LastTimeStartedLatchedJump。该已解析路径没有Walking、目标表面或普通入口的VSize>2检查。仍受UE请求归属、实际网络路由、耐力、动画执行及后续状态更新影响，不能据此宣称任意状态或速度都可行。

BlueprintAnimNotifyCustomEvent里明确分派：

- LatchedJumpStart → LatchedJumpStart()：把LatchedJumpVelcityInterpSpeed置0、CharacterMovement.GravityScale置0.001。
- LatchedJumpLaunch → Latched Jump Launched()：把CachedLatchJumpVelocity复制到LatchedJumpVelocity，清空缓存，恢复类默认插值速度与GravityScale，更新相关时间与朝向。

RidingTick在Falling且LatchedJumpVelocity非零时，对预期位移进行BPFastTrace；一条分支把该向量写入移动组件Velocity，另一条置零。该向量随后按LatchedJumpVelcityInterpSpeed向零收敛；当前实例默认插值速度为13000。没有将单位方向自动放大为起跳速度的步骤。

这给出“无需先真实抓住墙面，也许能请求动画起跳链”的具体候选，但名称不能作为可行性保证。也不能把准备阶段GravityScale=0.001称为永久悬停：已有速度可能继续造成位移，动画随后恢复重力。视频仍不能归因于此链。

## 其他入口筛查

- ServerRequestPounce入口0x2468直接POP_FLOW；ServerSetLocDuringLatchedJump入口0x127b同样直接退出。不能因函数名存在就当成有效入口。
- ServerSlideInputPressed/Released主要写并同步SlidingInputPressed；释放还清空滑动开始时间。没有在这两个处理里找到独立空中推进。
- ServerUpdateTransformDuringLatchedJump首先检查EnableServerUpdateTransformDuringLatchedJump；当前实例为false，Validation为true。不能通过改客户端同名值打开服务端入口。
- ServerRequestWaterSurfaceJump原生实现检查服务器MovementMode==Swimming，且有最近状态时间、状态组件/耐力等条件；不适合把它直接当成空中滑翔跳跃。
- Server_SetWantsForcedMovement有角色类型、骑乘/驾驶资格及输入枚举分支；未发现可直接作为任意悬停或速度向量入口的证据。

## 下一轮实验设计

优先验证一次自动跳跃链，不先做持续悬停：仅客户端，当前骑乘恐爪龙、Falling、无抓附目标时，单次触发已校验的自动跳跃入口，采用有限正常量级速度（例如水平10–20m/s、向上3–6m/s），保留原生耐力和动画过程。先验证服务器CachedLatchJumpVelocity、LatchedJumpVelocity、GravityScale和位置是否按通知链变化，再决定有无必要实现滑翔中的推进。

实验不应叠加本地LaunchCharacter、持续速度写入、自动续抓或伪造Walking，否则无法确定实际生效路径。当前只是设计，未新增功能/编译DLL，也未替用户操作游戏。若缓存能进入服务器但未施加速度，应先查动画通知，而不是继续提高数值。
