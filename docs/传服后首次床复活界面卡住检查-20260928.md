# 传服后首次床复活界面卡住检查（2026-09-28）

## 结论与验证范围

项目存在与“服务器人物已经复活、客户端还停在复活界面”高度吻合的缺陷：开启 `bFastRespawned` 后，Hook 直接丢弃整个 `ClientNotifyRespawned`，并非只跳过动画。分发目录 `dist/phoenix/cfg/phoenix_autosave.ini` 的该项为 `1`。

这是确定的代码缺陷，但尚不能断言是用户此次故障的唯一原因。检查时客户端 PID 为 43352，处于主菜单，仅发现菜单控制器实例；模块列表未发现 phoenix，且当前 ClientNotifyRespawned 入口没有 Hook 跳转。没有捕获到故障发生时的通知、角色与 HUD 状态。本次未修改源码、用户配置或游戏进程内存，未进行跨服复现。

## 代码证据

- `src/external/Minimal-D3D12-Hook-ImGui/Main/hooks.cpp`，`hkClientNotifyRespawned`：配置开启即 `return`，原始通知不执行；不区分首次下载生存者与普通死亡复活。
- 同文件 `initClientNotifyRespawned` 实际注册 Hook；与已停用的进服 Hook 不同，该入口仍在 `StartAllHooks` 中启用。
- `src/internal/Util/Util.h`，`FindUFunction` 返回 `UFunction::ExecFunction`。该入口是 UE 参数解析包装器，而 Hook 声明为 `(APrimalPlayerController*, APawn*, bool)`，与实际 `(UObject*, FFrame&, void*)` 不匹配。当前转发时把第三参数作为 bool 使用，不能认为关闭选项后该 Hook 的调用仍然可靠；编译器不保证保留被 bool 转换丢弃的指针信息。

## 当前安装版本的只读核对

反射和反汇编采样位于 `release/diagnostics/respawn-review-20260928`，客户端模块基址 `0x7ff6df680000`。以下地址为 RVA，只适用于本次版本：

- `PrimalPlayerController.ClientNotifyRespawned` Exec 入口为 `0x3e5f620`，从 FFrame 读取 Pawn 和 bool，再调用 vtable `+0x17c8`；证明 Hook 的目标并非接受 Pawn/bool 的普通函数体。
- `ShooterPlayerController` CDO 对应原生实现为 `0x66c3750`。开头更新控制器 `+0x1278` 的 `bIsFirstSpawn` 和 `bIsRespawning`，随后安排定时回调；因此这个通知承担客户端状态流转，不能整体吞掉。
- `HandleRespawned` 原生实现为 `0x66c3220`，根据首次出生参数走不同路径。首次下载和普通复活不能简单当成同一个动画分支。
- 当前版本提供 `ShooterHUD.CloseSpawnMenu`，Exec RVA `0x5fad020`；SDK 也提供角色 `ClearSpawnAnim`。这些只能作为后续恢复/动画修复候选，尚未验证足以修复此次故障。

## 可行处理

1. 对照测试：关闭菜单里的“跳过重生动画”，保存后重新进行传服、下载生存者、床复活。如果仍有问题，再进行一次不加载 phoenix 的相同流程，以排除通知 Hook 的签名问题和其它模块影响。
2. 已卡住时，关闭开关不会补发已经丢失的通知。可以先退出到主菜单再连接同一目标服务器，观察是否接回已存在的人物；这属于恢复尝试，尚未在此次故障状态下验证。不要以创建新人物作为恢复步骤。
3. 源码的保守修复是停止注册这个通知 Hook，完整保留原生出生流程；代价是暂时不提供跳过重生动画。若保留动画功能，应修正 Hook 签名并在原生流程完成后针对动画做处理，不能再整体拦截通知。首次下载应完整保留原生初始化。
4. 如果不加载 phoenix 也能复现，应在故障时只读采样控制器 Pawn/AcknowledgedPawn、bIsFirstSpawn/bIsRespawning、HUD 的复活面板，以及服务端是否已控制活着的人物。只有确认角色和控制权都已就绪，才适合调用原生关闭复活面板入口；不能按固定延时无条件关闭下载/复活界面。

建议回归覆盖：首次下载到床、首次下载到随机出生点、普通死亡床复活、退出重连，以及动画选项开关两种状态。当前尚无这些场景的通过记录。

## 2026-09-29 修复

用户确认关闭功能可以解决故障，并选择保留普通死亡复活的跳过行为、首次下载走完整流程。实现将 Hook 从 UE Exec 包装器移到该包装器调用的 ShooterPlayerController 原生虚函数体（当前 vtable 字节偏移 `0x17c8`，slot 761）。包装器继续完成 Pawn/bool 参数解析与栈推进，Hook 接收到真实 `IsFirstSpawn`。参数为 true 时始终调用原生实现；仅配置开启、非卸载、参数为 false 且控制器/Pawn 非空时保留旧跳过行为。没有手动关闭 UI、修改首次出生参数或改写用户开关。

入口安装先校验当前 Exec 包装器的参数转发和虚函数调用指令；不匹配时不安装 Hook，避免游戏更新后误用虚函数槽位。该策略以游戏给出的 `IsFirstSpawn` 为准，不自行推测下载状态。

`tests/run-respawn-notification-tests.ps1` 使用安装客户端采集的包装器字节固定样本，验证槽位识别、所有被校验指令的变更拒绝、截断拒绝、首次通知重试时原生收尾、普通复活跳过、关闭/卸载及空 Pawn 转发。样本保存为 `tests/fixtures/client-notify-respawned-20260928.hex`。通过模拟回归不能代替实际下载角色验证。

验证结果：上述回归通过；`build-release.ps1` 的 Release x64 DLL、启动器编译和启动器 `--check` 均通过，产物更新至 `dist/phoenix` 与 `dist/phoenix.zip`。编译日志为 `release/respawn-fix-build-20260929.log`。源码编译产物与分发 DLL 的 SHA256 一致：`C09B547167691D0E1645546351D19E7F438613607D24BA6FF90B7165467478AC`。分发配置的 `bFastRespawned=1` 保留。当前未运行游戏，未注入或执行跨服复现；请使用新版启动器重新加载后验证首次下载到床和普通床复活。
