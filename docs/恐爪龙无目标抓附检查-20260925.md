# 恐爪龙无目标抓附检查

用户需求：没有墙面或恐龙目标，在空中进入抓附姿态并保持，按空格加速脱离。此需求不同于靠近真实目标自动抓附。此前客户端运动 Hook 已执行速度写入，但用户确认仍会回拉，不能继续把直接写 Velocity 当作有效方案。

## 本轮只读核对

证据保存在 `release/diagnostics/deino-latch-review/`，使用前次本地测试服的蓝图字节码快照，并通过同一服务器进程的名字池解析调用名称。本轮没有发送候选抓附 RPC、修改游戏状态或部署新 DLL。

- `UberpounceCurrentData` 为 72 字节结构，包含 Socket、WorldGeoLocation、WorldGeoRotation、Character、Type、TargetIsFoliage。无目标不等于这些数据可以随意清零：后续更新会读取目标变换。
- `CheckForFallingLatchFn` 有 `AutoJumpAfterLatch` 输入，调用引用包含 `Has Latchable SurfaceWhileFalling`、`GetUberpounceTransform`、`ServerStartUberpounceFromFalling`。不能当作无目标抓附开关。
- `CanContinueUberpounce` 包含 Character 有效性分支；位置分支会求目标变换、比较当前位置和抓附位置的距离，并用胶囊半径及目标旋转构造 `VTraceSphereBP`。距离比较参数为 FloatConst 20（引擎位置单位）。检测结果参与返回值。
- `UpdateUberpounceFn` 在字节码 0x11e 调用 `CanContinueUberpounce`，并包含体力处理和多处 `MultiEndUberpounce`。已确认有持续更新中的有效性检查，但尚未完整还原每种状态的客户端/权威端分支，不能把全部结束调用归因于这个检查。
- 单独的 `IsValidUberpounceDataForLatching` 在该快照中只是把输出 Ret 设为 true。这不代表完整抓附流程无校验；它与后续持续性检查是不同函数。
- 抓附状态和类型枚举仅提供 NewEnumerator 名称，没有可信的显示名称映射。尚未据此猜测状态数值或发送虚构目标数据。

## 当前边界

不能据上述静态分析宣称无目标抓附绝对不可能，也没有证据证明仅切换本地抓附状态就会被服务器认可。需要继续还原状态更新和服务器分支，或者在用户选择自有本地服运行时修改后，让服务器主动支持该行为。后者属于服务端功能修改，不能描述成仅客户端即可在其他服务器复现。

用户已明确选择仅客户端，并要求直接修改打包后由其测试。不修改服务器内存、插件或模组。

## 客户端实验版

新增默认关闭的“恐爪龙无目标空中抓附（实验）”，配置 `bDeinoAirLatch`，停止自动化也会关闭。实现 `src/internal/Hack/DeinoAirLatch.inl`，由 FeatureExpansion 的游戏线程调度。

操作：骑恐爪龙，开启实验；关闭菜单，在正常下落且未抓附时轻按 F6。使用当前位置附近的合成世界坐标、空 Socket 和空 Character 构造候选数据，调用游戏自身的 GetUberpounceTransform 验证偏移并补偿，再各调用一次 ServerStartUberpounceFromFalling 和 StartUberpounceFromFalling。不会重复刷请求，不直接修改位置或冻结 Velocity。

候选数据的 Type 使用 0。补充核对 CheckForFallingLatchFn 的 0x44c 附近字节码，可见它清空 Character 并把对应数据的 Type 设为 ByteConst 0；不是根据枚举显示名称猜值。空 Socket 在已核对的 GetUberpounceTransform 中选择世界坐标分支。旋转使用侧向的候选表面姿态，能否在无实际碰撞表面时完成抓附状态转换仍需游戏内测试。

检查修改：进入前将客户端 CanContinueUberpounce 的前 14 字节临时改为设置输出 Ret=true 并返回。验证原脚本长度 568、入口和结尾序列、返回字段类型与参数大小后才修改；保留原数组与其余字节。该 UFunction 是客户端类共享的，因此实验期间同类实例的本地持续抓附检查也受影响，不是服务器判定修改，也不是只针对一个实例的函数替换。

脱离与恢复：轻按空格，以视角水平方向提交脱离速度，默认 30m/s、范围 1–100m/s，Z=0；再次 F6 则零附加速度退出。先恢复检查，再调用 ServerEndUberpounce 和本地 EndUberpounce。打开菜单、失焦、下骑、关闭功能及卸载均退出并恢复。已发生的位移不会倒放。只在函数仍有效、脚本指针一致且前 14 字节仍为本实验写入内容时恢复，避免覆盖其他更新。

为避免键位冲突，此实验开启时暂停之前的原生跳跃/悬停入口。原生 Space 输入仍由游戏处理，本功能不吞掉按键；游戏自己的脱离处理与请求可能相邻发生。其他服务器检查、体力消耗、错误位置纠正均保留，所以“不按空格一直保持”是本次待验证目标，不是已证明的效果。

已对运行中客户端重新抓取反射，核对 7 个入口与脚本签名，证据 `client-contracts.json`。旧快照对象名称不匹配时没有沿用旧指针。尚未自动执行游戏内操作，等待用户测试。

交付验证：Release 编译、启动器自检、功能配置持久化/停止清单回归与现有生产补丁测试通过；语言/归档校验为 926 键、723 文本。实验字节码恢复已代码审查，尚未进行游戏内实测。当前 DLL 被游戏占用，新版写入 `dist/phoenix/phoenix.dll.pending`，SHA256=`454f39fa163ccc9b509a51dfcd0616401920a2542adb4959d78177847d19c052`。完全退出游戏后再运行启动器应用更新。

## 自动续抓迭代

用户反馈：可以进入抓附，但瞬间结束；持续手动连按可以悬停。该反馈证明短时入口有效，尚未区分自动结束来自客户端状态机还是服务器，也不代表单次永久抓附成立。

新版沿用户已经观察到的重复进入方式实现自动续抓：F6 开始后保持启用意图，只有 UberpounceState 回到 0 且 MovementMode 为 Falling 时重新调用入口，两次提交间隔至少 250ms；仍处于抓附状态时不额外请求，卡顿后不补发积压请求。续抓前先恢复上次的字节码，再保存和应用新补丁，防止把 true 返回桩误保存成“原始值”。

空格或再次 F6 优先停止续抓并恢复检查，然后脱离；落地、输入暂停、失焦、菜单、下骑、关闭及卸载沿原恢复路径停止。校验失败立即停止，不连续发送失败请求。续抓候选锚点依然取当前实际位置，不强制拉回第一次锚点，因此不能承诺完全锁定高度或消除服务器纠正。

频率规则独立于游戏对象，`DeinoAirLatchRules.h` 的测试覆盖 250ms 边界、有效抓附时不重发、落地/无效状态不重发、同帧去重及卡顿后不突发补发。游戏内自动续抓和空格脱离效果等待用户反馈。

自动续抓版 Release 编译、启动器自检、上述频率规则及功能回归通过；语言/归档校验通过（930 键、727 文本）。新版直接部署到 `dist/phoenix/phoenix.dll`，SHA256=`0516003433236276191b5137429c59ea99568bc9f6210f81e74d4751637afcec`。

## 抓附结束后的运动模式过渡修复

用户反馈旧版提示“运动状态不支持”，无法连续抓附。代码确实把 `State==0 && MovementMode!=Falling` 直接当成停止条件，不能区分空中过渡模式与落地；尚未记录用户那一帧的具体模式值。

修复后，状态读取有效且非 Swimming 时，不再因 None / Flying / Custom 或 Walking / NavWalking 直接停止。等待 State 回到 0 并达到原有 250ms 提交间隔后，调用已核对参数的原生只读 `K2_FindFloor` 获取新的地面检测结果，不使用可能残留起跳前数据的 CurrentFloor。

只有可阻挡、可行走且距离在 -5 至 5 引擎单位内的地面才作为落地候选；第一次检测到时暂缓续抓，至少 250ms 后再次确认才退出。期间检测为空则清除确认状态并允许续抓。抓附仍有效时不重发。地面查询校验失败则暂停请求并提示原因，空格/F6退出仍优先处理。未取消服务器纠正或更改续抓频率。

新增离线用例覆盖各个过渡模式、游泳/无效模式排除、单次地面命中不误停、空中检测清除旧确认及两次确认落地。新的游戏内连续抓附效果仍需用户反馈。

## 空格改用抓附跳跃入口

用户反馈空格只解除抓附，没有加速。原实现空格与取消都调用 EndUberpounce，只是传入不同速度；这不能等同于调用游戏的抓附跳跃。

补查本地服 `ServerEndUberpounceFn`（737 字节）发现：ValidatedVelocity 先清零，非零输入经过抓附状态分支、LastTimeAppliedVelocityOnEndUberpounce 的 1.5 秒时间检查，并按服务器 LatchedJumpOffWallSpeed 限制模长。状态不匹配时也可能只发出零速度解除。以上为静态分支分析，没有动态捕获本次用户操作究竟命中哪一项。

空格现改为调用客户端 `LatchedJump`，使用核对后的 644 字节函数布局：JumpStrength=1、IsLatchedAutoJump=false、WallHugDirection=零向量、DirectionOverride=视角水平单位向量。调用期间按菜单速度临时调整 LatchedJumpSpeed、UberpounceLatchedJumpMaxSpeed、LatchedJumpWallHugSpeed 三个客户端字段，返回后条件恢复，交由函数自身计算速度、更新跳跃状态和选择请求路径。该入口仍可能受到服务器或其他原生条件限制，滑条不保证等于服务器最终速度。

顺序为：先停止自动续抓 → 调用原生抓附跳跃 → 恢复持续抓附检查。成功调用后不再追加 EndUberpounce，防止自己取消刚发出的跳跃。F6、菜单暂停、关闭功能等仍使用零速度取消；跳跃入口校验失败则退回取消并给出明确提示。原生 Space 输入没有被屏蔽。

当前客户端运行中 LatchedJump 的名称、大小和四个参数已再次只读核对，记录在 `latched-jump-client-contract.json`。本轮未进行游戏内效果测试。

## 脱离后的单次水平及向上起跳

用户反馈 LatchedJump 版仍只解除抓附、没有飞出。本轮保留抓附跳跃请求，新增独立向上速度 DeinoAirLatchReleaseUpSpeed，默认 6m/s、范围 0–30m/s；水平默认仍为 30m/s。跳跃方向使用水平朝向与向上分量合成的单位向量。

调用后至少等待 50ms，且 UberpounceState 回到 0 时，通过经参数校验的 Character.LaunchCharacter 追加一次水平及向上速度，XY/Z 均覆盖。等待总窗口为 500ms；期间 F6、下骑、关闭功能、菜单暂停或失焦会取消。脉冲调用前先消费请求，不累加、不重试。使用新的 K2_FindFloor 查询排除贴地，兼容抓附结束时的运动模式过渡，排除游泳和无效模式。
